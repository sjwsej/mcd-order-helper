# 规则与实现细节

这份文档解释脚本为什么这么算，以及要改规则时动哪里。

## 0. 门店：必须由用户选定，没有默认

脚本**不读收藏门店、不自动挑一家**。`pick_store()` 只认 `--store`，
没有就直接抛 `MissingStore`（退出码 5）并打印引导。

搜索走 `query-nearby-stores` 的 `searchType=2`，参数是 `city` + `keyword`：

| 传参 | 实测结果 |
|---|---|
| `city=上海, keyword=徐家汇` | 5 家（含距离、营业状态） |
| `city=北京, keyword=`（空） | **0 家** |
| `searchType=1`（收藏门店） | 已弃用，不再调用 |

所以 `--city` 与 `--keyword` 必须同时给，且关键词用商圈/路名/地铁站比商场全名更容易命中。

候选列表按「营业中优先 → 距离由近到远」排序，`*` 标记营业中，供用户自己挑。

## 1. 数据链路

```
query-nearby-stores    → 门店 storeCode / beCode / 营业状态
query-meals            → data.categories[]（分类）+ data.meals{code}（名称、现价、原价、discountType）
query-meal-detail      → 套餐的 data.rounds[]（选配轮次，含默认选项）
calculate-price        → data.price（单位：分，含优惠后的实价）
```

外送场景（beType=2/6）需要 `beCode`，脚本已按 beType 自动决定 orderType：
`beType ∈ {1,5}` → `orderType=1`；`beType ∈ {2,6}` → `orderType=2`。

## 2. 一份菜单怎么变成"可组合单元"

`menu_model.build_units()` 把每个 SKU 变成一个 `Unit`，关键字段
`provides = (staple, snack, drink, dessert)` —— 这个商品能提供几个主食/小食/饮料/甜点。
有了它，"一篮子里到底几个汉堡、几杯可乐"就是加法，不靠猜。

### 2.1 角色判定顺序（不可颠倒）

1. **非食品**（按摩捶、玩具、周边）→ 其他
2. **调味酱**（以"酱"结尾且不含食物主体词）→ 其他
3. **甜点**（麦旋风、新地、圆筒、冰淇淋、派…）
4. **饮料**（可乐、雪碧、红茶、牛奶、咖啡、果汁、柠、怡泉、麦炫酷…）
5. **主食**（堡、卷、汉堡、**麦香鸡**）
6. **小食**（薯条、薯饼、鸡翅、麦乐鸡、鸡块、鸡排、玉米杯、苹果片、芝士条…）

两个容易踩的坑：

- `麦香鸡` 是汉堡但不含"堡"字，必须写进主食词表，否则会被"鸡"抢去判成小食。
- `柠檬脆脆麦旋风` 含"柠"，所以**甜点必须排在饮料之前**判。

### 2.2 套餐的组成：不看名字，看 rounds

名称里的"N 件套"只能猜（`n 件套 = 1 主食 + (n-2) 小食 + 1 饮料`），实际以
`query-meal-detail` 的 `rounds` 为准，每个 round：

1. 取默认选项（`quantity>0`，其次 `isDefault=1`）的名称判角色；
2. 判不出来再退到 round 名称（含"饮料/饮品"→饮料，"小食/甜点/配餐/蘸酱"→小食）；
3. 都不匹配且 round 名不像食物（玩具）→ 其他，不计入件数。

实测参考：

| 商品 | rounds 结构 | 判定结果 |
|---|---|---|
| 巨无霸四件套 | 巨无霸 / 小食 / 小食 / 饮料 | 1 主食 + 2 小食 + 1 饮料 |
| 板烧鸡腿堡三件套 | 板烧鸡腿堡 / 小食 / 饮料 | 1 + 1 + 1 |
| 人气经典随心配（1+1） | 蓝区（双层吉士汉堡）/ 粉区（红茶） | 1 主食 + 1 饮料 |
| 精选超值随心配（1+1） | 蓝区（鸡排）/ 粉区（红茶） | 0 主食 + 1 小食 + 1 饮料 |
| 蘸酱BFF四宫格 | 小食×3 / 蘸酱 / 小食 | 0 主食 + 5 小食 |
| "辣"么快乐套餐 | 麦辣鸡翅 / 麦乐鸡 / 饮料 | 0 主食 + 2 小食 + 1 饮料 |

「蓝区」按**默认选项**判：默认是汉堡就算主食，默认是鸡排就算小食（用户实际拿到的是默认那份）。

### 2.3 价格：必须校正"随单购麦金卡"

菜单 `currentPrice` 对 `discountType` 含「随单购」的餐品是**有卡价**。
实测：板烧鸡腿堡四件套菜单写 28，`calculate-price` 实算 **57**。

所以默认（`--card no`）按 `originalPrice` 计价，并保留 `cardPrice` 供提示。
用户说"我有麦金卡"才传 `--card yes`（或 `--with-card`），此时按卡价算，但输出会标`〔需麦金卡〕`。

## 3. 约束（对应需求原文）

| 编号 | 约束 | 默认值 | 参数 |
|---|---|---|---|
| C1 | 篮子里主食数量 == 目标值 | — | `--staple` |
| C2 | 饮料数 ≤ `ceil(主食数 × 4/3)` | 超 1/3 | `drink_cap_for()` |
| C3 | 品类多模式：不含主食的套餐 ≤ 2 个 | 2 | `--max-no-staple-combo` |
| C4 | 小食 + 甜点件数 ≤ 主食数 + 2 | 主食+2 | `max_extra_snack` |
| C5 | 品类多总价 ≤ 同档省钱价 × 2 | 2.0 | `--price-limit` |
| C6 | 儿童餐份数 ≤ 儿童人数 | 0 | `--kids N` |

C2 的取整：主食 1→2 杯、2→3 杯、3→4 杯、4→6 杯、5→7 杯。
"最多超过三分之一"按**主食数的 1/3 向上取整**宽松化处理。

C3 里的「不含主食的套餐」指 `is_combo && provides[0]==0` 的单元，
例如 BFF 四宫格小食盘、学生专享饮品随心选、精选超值随心配（蓝区默认是鸡排时）。

C4/C5 是工程护栏 —— 需求原文只限制了"附加套餐 ≤ 2 个"，
但只放开这个会导致品类多模式堆出十几样、上百元的小票，所以补了两条下限约束。

C6 的判定：名称含「开心乐园 / 亲子餐 / 儿童餐」的单元标 `is_kids`。
`--kids 0` 时这些单元不进候选池（等价于排除）；`--kids 2` 时最多出现 2 份。
注意它是**份数上限**，不是"必须点儿童餐"。

## 3.1 麦金卡与儿童配套（实测）

| 场景 | 参数 | 效果 |
|---|---|---|
| 无卡 | `--card no`（默认） | 麦金卡类餐品按原价算；板烧四件套 ¥57（菜单标 28） |
| 有卡 | `--card yes` | 按卡价算；同一份四件套 ¥28，整体价格会明显下移 |
| 无小孩 | `--kids 0`（默认） | 开心乐园餐/亲子餐不进组合 |
| 带 1 个 | `--kids 1` | 最多 1 份，实测 2 主食品类多模式下基准从 ¥52.9 → ¥48.4 |
| 带 2 个 | `--kids 2` | 最多 2 份，基准 ¥57.5（两份乐园餐 + 饮品） |

## 4. 排序

```
cheap   : (价格, -品类数, -件数)
variety : (-品类数, -件数, 价格)
```

- **品类数 `kinds`** = 不同单元贡献的食物件数之和，同款只算一次。
  例：2 个"板烧四件套"→ 4 种（不是 8 种）。
- **件数 `items_total`** = 含重复的总件数。

## 5. 推荐阶梯

| 位置 | 内容 |
|---|---|
| 基准 | 主食数 = N 的最优解，作为对照锚点 |
| 推荐 1 | 主食数 = **N-1** 的最优解（N=1 时自动跳过） |
| 推荐 2 | 主食数 = **N+1** 的最优解 |
| 推荐 3+ | N 档的第 2~3 名（须不被基准支配）+ N±2 … N±span，**按倾向统一排序** |

"被基准支配"指：更贵且品类数没变多，这种方案没有推荐价值，直接剔除。

每条推荐都带 `delta`：相对基准的价格差、品类数差、各角色数量差，以及拼好的中文描述。

## 6. 搜索规模控制

暴力枚举会爆炸（80 个 SKU 的自由组合），所以：

1. 每个角色池按价格排序截断：主食单品 8 个、小食 12、饮料 8、甜点 6、
   含主食套餐 10、不含主食套餐 6；
2. 先用"基底价 + 必要饮料"粗排，只对前 40（品类多 120+60）个基底做完整补齐；
3. 套餐使用数 ≤ `min(3, 目标主食数)`；
4. 主食允许重复（`combinations_with_replacement`），否则"来 2 个同款汉堡"会搜不到。

实测 2~6 个主食的完整阶梯约 3~5 秒。

## 7. 要改规则时动哪里

| 想改什么 | 改这里 |
|---|---|
| 门店搜索方式（比如接定位） | `order_helper.search_stores()`；筛选/排序在 `--list-stores` 分支 |
| 某商品分类判错 | `menu_model.py` 的 `STAPLE_KW / SNACK_KW / DRINK_KW / DESSERT_KW` 或 `_is_condiment()` |
| 辣度判定 | `menu_model.py` 的 `SPICY_KW / MILD_KW`；辣度只约束**主食** |
| 饮料上限比例 | `optimizer.drink_cap_for()` |
| 附加小食上限 | `optimizer.optimize()` 的 `max_extra_snack = target + 2` |
| 品类多的目标函数 | `optimizer._sort_key()` / `_fill()` 里的贪心评分 |
| 推荐条数 | `--span`、`same_tier_extra` |
| 套餐组成缓存刷新 | 删 `.cache/` 或加 `--refresh` |

## 8. 已知局限

- 辣度按名称关键词判定，属于启发式；新品的辣/不辣可能判错，必要时手改 `SPICY_KW`。
- 套餐组成取的是**默认选配**；用户在 detail 里换中薯条→大薯条会多收 1.5 元，脚本不计这部分差价。
- 未接优惠券：`calculate-price` 不带 `couponId` 时是券前价。要券后价需先查 `query-store-coupons`。
- 不来「随心配蓝区换汉堡」这种操作 —— 默认给什么就算什么，需要时手动指定。
